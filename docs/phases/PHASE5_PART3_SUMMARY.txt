OVERVIEW
================================================================================

This phase built the centralized audit orchestration layer that manages all 7
audit modules through a single execution engine. Pages are fetched ONCE and
shared across all selected modules, eliminating duplicate HTTP requests.

Key deliverables:
1. AuditOrchestrator - centralized execution engine
2. PageFetchService - shared page fetching with in-memory cache
3. ModuleRegistry - single source of truth for all modules
4. AuditSummaryService - project and module-level summaries
5. AuditResultHelper - consistent result formatting
6. AuditEngineController + route - single API entry point
7. Audit configuration file (config/audit.php)
8. Fixed autoloader (App\ prefix now resolves correctly)
9. All processors refactored with processHtml() method
10. Frontend updated to use orchestrated single-request execution

================================================================================
ARCHITECTURE
================================================================================

BEFORE (per-module execution):
  UI → Module A endpoint → fetch page → analyze → store
  UI → Module B endpoint → fetch page → analyze → store  (DUPLICATE FETCH!)
  UI → Module C endpoint → fetch page → analyze → store  (DUPLICATE FETCH!)

AFTER (orchestrated execution):
  UI → Audit Engine → fetch page ONCE → share HTML to all modules → store all

PERFORMANCE GAIN:
  7 modules × N pages = 7N HTTP requests  →  1N HTTP requests
  (7× fewer outbound requests to target sites)

================================================================================
EXECUTION FLOW
================================================================================

1. User selects modules and clicks "Run Selected Audits"
2. Frontend sends single POST to /routes/audit_engine.php?action=run_project
3. AuditEngineController validates input and builds module params
4. AuditOrchestrator::runProject() is called
5. ModuleRegistry::resolve() validates and orders selected modules
6. For each page in project:
   a. PageFetchService::fetch() retrieves HTML once (cached in memory)
   b. Each selected processor's processHtml() is called with shared HTML
   c. Results are stored via each module's repository
   d. History is recorded if status changed (AuditHistoryService)
   e. Memory cache cleared for that URL to keep footprint low
7. AuditRunService records completion and execution stats
8. Frontend receives summary and refreshes the workspace

================================================================================
SHARED PAGE FETCHING
================================================================================

PageFetchService:
  - Centralized cURL-based fetcher
  - In-memory LRU cache (max 50 entries, configurable)
  - Auto-eviction of oldest entries when cap reached
  - Per-URL forget() after processing to minimize memory
  - Shared response includes: html, http_code, final_url, content_type, error
  - All modules receive the same HTML string (no duplicate requests)

Memory optimization:
  - Cache cleared per page after all modules process it
  - Max 50 entries prevents memory bloat on shared hosting
  - No disk caching (stateless between requests)

================================================================================
RESULT CONSISTENCY
================================================================================

Every module result (via processHtml) returns at minimum:
  - status: PASS | WARNING | FAIL | ERROR
  - error: string|null
  - Module-specific data fields

AuditResultHelper::normalize() creates the unified envelope:
  - module_name
  - status
  - summary (human-readable)
  - details (raw module data)
  - execution_time
  - checked_at

AuditResultHelper::buildSummary() generates per-module descriptions:
  - "Single H1 found"
  - "Title: valid, Description: too_short"
  - "3 placeholder occurrence(s)"
  - etc.
