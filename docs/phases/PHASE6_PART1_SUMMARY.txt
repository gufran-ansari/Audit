OVERVIEW
================================================================================

Implemented a background job processing system that allows audits to run
independently of the UI. Users can queue an audit and continue working while
the system processes pages in batches. Designed for shared hosting with
limited execution time and memory.

================================================================================
BATCH PROCESSING
================================================================================

Design for shared hosting:
  - Default batch size: 25 pages
  - Max execution time: 55 seconds per invocation
  - Memory-friendly: clears fetch cache after each page
  - Resumable: stores last_page_id for continuation
  - Interruptible: heartbeat timeout detection (120s)

Processing loop:
  1. Get next batch of pages (ordered by ID, after last_page_id)
  2. For each page: fetch once → run all modules → store results
  3. Update progress + heartbeat after each batch
  4. If time limit reached: save progress and exit (will resume next run)
  5. If all pages done: mark job as completed

================================================================================
HEARTBEAT & INTERRUPTION DETECTION
================================================================================

During processing, the job updates last_heartbeat:
  - After each batch completes
  - Via updateProgress() call

Detection:
  - Jobs with status='processing' and last_heartbeat > 120 seconds old
  - markAllInterrupted() scans for and marks these jobs
  - Called by cron script and frontend polling

This handles:
  - PHP execution timeout
  - Server crash/restart
  - Network interruption
  - Manual process kill

================================================================================
API ENDPOINTS
================================================================================

POST /routes/jobs.php?action=create
  Params: project_id, modules, keyword (optional), batch_size (optional)
  Response: { success, job }

GET  /routes/jobs.php?action=process
  Response: { success, job_id, job }
  (Processes one batch of the next queued job)

POST /routes/jobs.php?action=run
  Params: job_id
  Response: { success, job }

GET  /routes/jobs.php?action=status&job_id=X
  Response: { success, job }

GET  /routes/jobs.php?action=list&project_id=X
  Response: { success, jobs }

GET  /routes/jobs.php?action=counts&project_id=X
  Response: { success, counts: {queued, processing, completed, ...} }

POST /routes/jobs.php?action=pause
  Params: job_id
  Response: { success, message }

POST /routes/jobs.php?action=cancel
  Params: job_id
  Response: { success, message }

GET  /routes/jobs.php?action=logs&job_id=X
  Response: { success, logs }

================================================================================
CRON SETUP
================================================================================

Add to crontab (recommended):

  * * * * * php /path/to/Audit/cron/process_jobs.php >> /path/to/Audit/storage/logs/cron.log 2>&1

Without cron (shared hosting):
  - Frontend automatically triggers /routes/jobs.php?action=process every 5s
  - Processing occurs as long as user has the page open
  - Jobs resume when user returns to the workspace

================================================================================
EXECUTION MODES
================================================================================

The system now supports two execution modes:

1. SYNCHRONOUS (existing, via audit_engine.php)
   - User clicks → waits → sees results
   - Best for small projects (< 50 URLs)
   - Uses AuditOrchestrator directly

2. BACKGROUND (new, via jobs.php)
   - User clicks → job queued → returns immediately
   - Best for large projects (100+ URLs)
   - Processed in batches by JobProcessor
   - Progress visible in real-time via polling
